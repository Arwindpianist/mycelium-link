## 4. The Technology: How MyceliumLink Works

### Core Concept: Blockchain-Verified Distributed Storage

MyceliumLink combines three proven technologies in a novel architecture:

1. **Content-addressable storage** (from IPFS)
2. **Distributed peer-to-peer replication** (from BitTorrent)
3. **Blockchain-based integrity verification** (from distributed ledger technology)

The result is a system that delivers:
- **Torrent-level efficiency** for large file distribution
- **Blockchain-level trust** for data integrity
- **IPFS-style permanence** for content addressing
- **Traditional cloud-level accessibility** through simple APIs

### Three-Layer Architecture

**1. Data Fragmentation Layer**
- Handles AES-256-GCM encryption and Reed-Solomon erasure coding
- Splits files into 100-150 fragments with 50% redundancy
- Manages content addressing and hash generation (SHA-3-256)

**2. Consensus Layer (Proof of Link)**
- Validates node uptime, storage integrity, and bandwidth contribution
- Uses Byzantine Fault Tolerance (BFT) for consensus
- Rewards nodes based on reliability score and geographic value

**3. Metadata Chain (Blockchain)**
- Immutable ledger for storage proofs and fragment locations
- Records ownership, access permissions, and compliance metadata
- Enables cryptographic verification without storing data on-chain

### How Data Flows Through MyceliumLink

#### Step 1: Upload and Client-Side Encryption

When a user uploads a file to MyceliumLink:

```
Original File (example.mp4, 1GB)
    ↓
Client-side AES-256-GCM encryption
    ↓
Encrypted Blob (encrypted_example.bin)
    ↓
Cryptographic hash generation (SHA-256)
    ↓
Content address: QmX7f3h2k... (unique identifier)
```

**Critical security principle**: Files are encrypted on the client side before ever leaving the user's environment. Neither MyceliumLink nor node operators can read the plaintext content. Only users holding the decryption key can access the original data.

#### Step 2: Smart Fragmentation

The encrypted blob is fragmented using erasure coding (Reed-Solomon algorithm):

```
Encrypted File (1GB)
    ↓
Split into 100 fragments (10MB each)
    ↓
Generate 50 redundancy fragments (150 total fragments)
    ↓
Minimum 100 of 150 fragments needed for reconstruction
```

This provides **50% redundancy**: even if half the fragments are lost (entire nodes going offline permanently), the file remains fully recoverable.

Erasure coding is superior to simple duplication because:
- **Space efficient**: 1.5x overhead vs. 3x for triple replication
- **Failure tolerant**: Any 100 of 150 fragments work (vs. needing specific copies)
- **Performance**: Can reconstruct from fastest responding fragments, ignoring slow nodes

*[Diagram placeholder: Visual representation of file fragmentation and erasure coding]*

#### Step 3: Geographic Distribution

Fragments are distributed to nodes based on:

**Geographic diversity**: Fragments spread across different regions, countries, and continents to prevent regional failures (natural disasters, internet outages) from causing data loss.

**Node reliability scores**: Nodes with proven uptime and fast response receive priority for fragment storage.

**Economic optimization**: Nodes offering competitive pricing (lower storage costs per GB) receive fragment assignments, creating a marketplace for efficiency.

**Regulatory compliance**: For data with residency requirements, fragments are constrained to nodes within compliant jurisdictions.

```
Fragment Distribution Example:
- Fragments 1-30: Malaysia nodes
- Fragments 31-60: Singapore nodes  
- Fragments 61-90: India nodes
- Fragments 91-120: Australia nodes
- Fragments 121-150: Thailand nodes
```

#### Step 4: Blockchain Metadata Registration

Once fragments are distributed, metadata is recorded on the MyceliumLink blockchain:

```javascript
{
  contentAddress: "QmX7f3h2k...",
  fragmentCount: 150,
  redundancyThreshold: 100,
  encryptionAlgorithm: "AES-256-GCM",
  fragmentMap: {
    fragment_001: { node: "node_MY_001", hash: "abc123...", size: 10485760 },
    fragment_002: { node: "node_SG_003", hash: "def456...", size: 10485760 },
    // ... 148 more fragments
  },
  owner: "0x742d35Cc6634C0532925a3b844Bc9e7595f0bEb",
  timestamp: "2025-10-12T08:30:00Z",
  expirationDate: "2026-10-12T08:30:00Z"
}
```

This blockchain record:
- Proves when data was uploaded
- Identifies where fragments are stored
- Creates an immutable audit trail
- Enables verification without revealing content

**Important**: The blockchain does NOT store the data itself—only metadata about where fragments exist. This keeps blockchain storage costs minimal while providing verification benefits.

#### Step 5: Proof-of-Storage Verification

Node operators must periodically prove they still possess the fragments they claim to store. This prevents nodes from:
- Deleting data but continuing to claim storage rewards
- Reporting fake storage capacity
- Free-riding on the network

**Challenge-response protocol**:

```
1. Blockchain randomly challenges: "Node MY_001, prove you have fragment_042"
2. Node responds with Merkle proof containing fragment_042 hash
3. Blockchain verifies hash matches original fragment registration
4. If valid → node earns uptime credits
5. If invalid → node loses reputation score and may be ejected
```

Challenges occur randomly and frequently (every 15-30 minutes per node), making it economically infeasible to fake storage.

#### Step 6: Retrieval and Reconstruction

When a user requests a file:

```
User requests: QmX7f3h2k...
    ↓
Query blockchain for fragment map
    ↓
Request fragments from multiple nodes in parallel
    ↓
First 100 fragments to arrive are used (others ignored)
    ↓
Erasure coding reconstructs encrypted blob
    ↓
Client-side decryption using user's private key
    ↓
Original file delivered
```

**Performance optimization**: By requesting fragments from many nodes simultaneously and accepting the first 100 responses, MyceliumLink automatically routes around slow or offline nodes. Users always get fast retrieval without manual selection of servers.

### Consensus Mechanism: Proof-of-Link

Traditional blockchains use:
- **Proof-of-Work** (Bitcoin): Wasteful energy consumption, slow
- **Proof-of-Stake** (Ethereum 2.0): Favors wealthy participants

MyceliumLink introduces **Proof-of-Link** (PoL):

Nodes earn influence and rewards based on:
- **Storage capacity contributed** (30% weight)
- **Uptime reliability** (30% weight)
- **Bandwidth provided** (20% weight)
- **Response time/latency** (10% weight)
- **Geographic diversity value** (10% weight)

This creates incentives aligned with network health: the most reliable, well-connected, geographically distributed nodes gain the most influence and income.

**Consensus process**:
1. Nodes with high PoL scores become "Validator Nodes"
2. Validator Nodes verify storage proofs from other nodes
3. Block production rotates among validators proportional to PoL scores
4. Invalid proofs are challenged by other validators
5. Consensus is reached when 67% of validators agree

This is efficient (thousands of transactions per second) and fair (anyone can become a validator by providing valuable resources).

### Blockchain Layer Design

**Blockchain platform**: Custom layer-1 blockchain optimized for storage metadata (alternative: Polygon/Arbitrum layer-2 for Ethereum compatibility)

**Block structure**:
```
Block Header:
- Block number
- Previous block hash
- Merkle root of transactions
- Validator signature
- Timestamp

Block Body (Transactions):
- File upload metadata
- Fragment location updates
- Storage proof verifications
- Node registration/deregistration
- Governance proposals and votes
```

**Transaction types**:
1. **UPLOAD_METADATA**: Record new file storage
2. **STORAGE_PROOF**: Node proves fragment possession
3. **FRAGMENT_MIGRATION**: Update fragment location when nodes change
4. **NODE_REGISTRATION**: New node joins network
5. **SLASH_INVALID_NODE**: Penalize misbehaving node

- Block time: 3 seconds
- Finality: 10-15 seconds
- Throughput: 5,000+ transactions per second
- Validator set: 50-100 nodes (rotates based on PoL scores)

#### Attack Mitigation

**Sybil Attack** (one operator creates many fake nodes):
- *Mitigation*: Proof-of-Link requires actual storage and bandwidth provision
- Economic cost of running many nodes exceeds potential rewards

**Data Ransom** (malicious nodes refuse to serve fragments):
- *Mitigation*: Erasure coding means 50% of nodes can go malicious without data loss
- Nodes refusing service lose reputation and earnings

**Storage Proof Fraud** (nodes claim storage without actually storing):
- *Mitigation*: Random challenge-response protocol makes fraud detection nearly certain
- Slashing penalties make fraud economically irrational

**DDoS Attack** (overwhelming node requests):
- *Mitigation*: Distributed architecture means no single point of attack
- Rate limiting and request authentication prevent amplification

**51% Attack** (controlling majority of validator nodes):
- *Mitigation*: High cost of acquiring 51% of network PoL score
- Governance can force validator rotation in attack scenarios

## 6. The Credit and Incentive System

### Economic Design Principles

MyceliumLink's economic model is designed around three core principles:

1. **Participation Rewards**: Contributors earn credits proportional to value provided
2. **Usage-Based Pricing**: Users pay only for resources actually consumed
3. **Network Sustainability**: Economic model funds ongoing development and security

### Storage Credit System (SCS)

**SCS** is the economic mechanism powering the MyceliumLink network, designed for simplicity and regulatory compliance.

**Credit Mechanics**:
- **Earned**: Node operators earn credits based on storage provided, uptime, and bandwidth served
- **Spent**: Users spend credits to pay for storage and bandwidth consumption
- **Transferable**: Credits can be transferred between users or converted to fiat currency
- **Stakeable**: Credits can be staked to operate validator nodes (future implementation)

**Economic Logic**:
```
Credit Value = Network Utility ÷ Total Credits in Circulation
```

As network utility (storage, bandwidth, users) grows faster than credit issuance, credit value appreciates, creating sustainable incentive alignment.

**Credit Earning Rates**:
- **Storage**: 1 credit per GB stored per month
- **Bandwidth**: 0.1 credits per GB served
- **Uptime bonus**: 1.2x multiplier for 99%+ uptime
- **Geographic bonus**: 1.1x multiplier for underrepresented regions

**Credit Spending Rates**:
- **Storage**: 1 credit per GB stored per month
- **Bandwidth**: 0.1 credits per GB downloaded
- **API calls**: 0.001 credits per request (first 10,000 free monthly)

**Initial MVP approach** (fiat-based):
To simplify early adoption, the MVP uses traditional payment methods (credit cards, bank transfers) with credits denominated in USD/RM. Credit system launches with fiat backing, token migration happens in beta phase.

**Future Token (MYCO) Distribution** (post-MVP implementation):

- **Geographic routing**: Content served from nearest node automatically
- **Cost advantage**: 70-80% cheaper than traditional CDNs

**Market opportunity**: $15B+ CDN market growing at 25% annually

MyceliumLink nodes with spare compute capacity can execute serverless functions:

// Example: Image processing function running on MyceliumLink
